# ThinkPad 唤醒后停留在报错文字画面：诊断与保留窗口救援

记录时间：2026-11-12，Ubuntu 本机。当前结论是**显卡与桌面睡眠恢复链路存在异常，另发现 ACPI 固件方法越界错误；尚未确认唯一根因，也未证明已经根治**。

用户所说的“永久黑屏”具体指：**屏幕一直显示类似 ACPI 报错的文字，长时间无法回到原图形桌面的登录/解锁界面**。后续按这个现象核对活动控制台与图形会话。

## 先记住这条救援路径

下次开盖持续黑屏，若上面还有 ACPI 报错文字，可先按 **Ctrl+Alt+F2**，尝试直接切回本次登录的原桌面。如果未恢复，再尝试文字终端救援，保留原来的图形会话：

1. 按 **Ctrl+Alt+F3**。
2. 如果出现文字登录界面，用 `mac` 和自己的登录密码登录；密码输入时没有字符回显。
3. 执行下面的命令，**不要加 sudo**：

   ```bash
   python3 ~/.local/lib/laptop-resume/resume_helper.py wake
   ```

工具会先保存日志，再尝试打开原 X11 会话的屏幕电源、重置屏保计时、切回原桌面。它会自动找原 GNOME 的显示地址与认证文件；无需在文字终端手工设置 `DISPLAY`。锁屏仍须正常输入密码。

Linux 可以让同一块屏幕切换显示不同的虚拟控制台。本次原图形桌面运行在编号 2 的 `tty2`；**Ctrl+Alt+F2 的含义是请求显示第 2 个控制台**。它不会重新创建桌面、注销或关闭应用；若原桌面已经卡住，切换也可能无效。下次登录后编号可能变化，工具输出的 `VT` 是当时实际位置。

这是一种保留会话的恢复尝试，**成功返回不等于屏幕一定恢复**。没有执行过故障现场恢复验证。如果连文字终端也无法显示，或者图形驱动已经死锁，这条路径可能无效。没有一种可以保证保住所有 GPU 应用的通用驱动重置命令。

不要把 `systemctl restart gdm3`、重启 `display-manager`、注销、杀掉 Xorg/GNOME、重置 GPU 当成这条救援路径；这些操作可能终止工作窗口。本工具不执行这些操作，也不解锁、重启、挂起或关闭电脑。

## 已经安装的自动取证

已新增用户级服务 `laptop-resume-monitor.service`，直接监听系统 logind 的 `PrepareForSleep` 信号，独立于锁屏界面能否显示。服务会在正常图形登录时启动。

- 记录进入睡眠和恢复的事件时间。
- 用户进程能够继续运行后，在唤醒约 **3 秒、45 秒**分别采集一次快照；实际调度和命令执行可能更晚。
- 从准备睡眠开始，每秒记录活动控制台和原 Xorg/GNOME 主进程的运行/等待状态，持续约三分钟可运行时间；睡眠期间暂停。记录不依赖“唤醒完成”信号，文件为 `transition-trace.jsonl`，512 KiB 轮换一份。
- 准备睡眠信号还安排一份延时取证：如果迟迟没有“唤醒完成”信号，而用户进程已能运行，仍会查询桌面、锁屏与显卡的响应。
- 保存内核显卡日志、Xorg 日志末尾、GNOME 错误、原会话、进程状态、RAM/交换区、显存和显示器状态。
- 额外记录 Xorg/GNOME 各线程等待位置、桌面 D-Bus 响应和锁屏查询响应；接口响应成功不能替代画面恢复确认。
- 优先落盘内核与进程证据，再查询可能卡住的显示/GPU 接口。
- 自动快照最多保留最近 **12 份**，目录仅当前用户可访问。事件日志到 256 KiB 后轮换一份。
- **只采集，不自动尝试恢复，也不改变合盖、锁屏或睡眠策略。**

即使当时打不开 Codex，只要内核和用户态恢复运行，服务仍可留下证据。若整机在恢复用户进程之前就卡死，无法保证生成唤醒后的快照；此前已落盘的事件及系统日志仍可用于排查。日志位于用户目录，不会因为普通重启而主动删除。

安装位置：

```text
~/.local/lib/laptop-resume/resume_helper.py
~/.config/systemd/user/laptop-resume-monitor.service
~/.local/state/laptop-resume/events.jsonl
~/.local/state/laptop-resume/snapshots/
```

查看服务和最近记录，在普通终端或文字终端执行：

```bash
systemctl --user status laptop-resume-monitor.service --no-pager
journalctl --user -u laptop-resume-monitor.service -n 30 --no-pager
ls -lt ~/.local/state/laptop-resume/snapshots/
```

额外手工采集，不做恢复：

```bash
python3 ~/.local/lib/laptop-resume/resume_helper.py collect
```

手工 `collect` 和 `wake` 的证据默认放在输出提示的私有 `/tmp/laptop-resume-*` 目录，`/tmp` 内容不保证跨重启保留。需要持久保存时指定一个尚不存在的目录：

```bash
mkdir -p ~/laptop-resume-evidence
python3 ~/.local/lib/laptop-resume/resume_helper.py collect \
  --output "$HOME/laptop-resume-evidence/$(date +%Y%m%d-%H%M%S)"
```

如以后不再需要自动取证，可停止并取消自启动，已有证据保留：

```bash
systemctl --user disable --now laptop-resume-monitor.service
```

本次启动更早的 Intel 日志还包含：

```text

i915 ... PHY B failed to request refclk
```

它们提示 Intel 显示路径也需要排查，但不能直接认定为最后一轮黑屏的原因。Xorg 的 `NVIDIA(0): Setting mode "NULL"` 本身也不等于显示损坏，因为该会话的内屏由 Intel 输出。

现有证据将嫌疑集中到双显卡、Xorg/GNOME 的睡眠恢复交互；**尚未捕获一次登录画面彻底无法恢复时的现场，无法判定是 GPU 卡死、显示输出未恢复，还是锁屏/桌面绘制卡住**。

## 后续修复应如何选择

1. **先用自动取证覆盖下一次自然发生的合盖。** 本次没有主动触发睡眠回归，避免给未保存的工作增加风险。若发生黑屏，先走文字终端救援；恢复后可直接分析持久化证据，无需当时打开 Codex。
2. **不要重复添加已经生效的显存保存选项。** 当前保存选项、备份路径和服务链路均存在，通用教程中“开启 PreserveVideoMemoryAllocations 和 resume 服务”的方案不构成本机的新修复。
3. **后续维护窗口可以验证 NVIDIA 的 S0ix 电源管理路径。** 本机平台和 GPU 都报告支持，当前却未启用。可把 `NVreg_EnableS0ixPowerManagement=1` 作为一个单独实验变量，比较连续合盖恢复、驱动错误与耗电。它仍是假设，不能承诺根治；这是模块加载参数，当前不为此卸载正在使用的 GPU 驱动。
4. **如证据定位到 NVIDIA 桌面渲染路径，再评估 Intel 桌面 + NVIDIA 按需模式。** 这会改变图形会话，且 Intel 输出自身也有报错，因此现在不切换、不注销；不能声称它已解决问题。
5. **如证据定位到 i915 或锁屏绘制，再做对应的单项验证。** 不同时改 PSR、刷新率、内核、驱动与桌面模式，否则无法判断哪项有效。

本机没有暴露 `deep` 睡眠，不能靠添加 `mem_sleep_default=deep` 创造固件不提供的 S3 支持。也没有把“合盖保持全速运行”设置为默认方案：你需要经常把笔记本装包移动，持续运行会带来耗电和散热问题。正常睡眠本应保留窗口，只是暂停程序运行。

NVIDIA 官方说明显存保存机制、S0ix 条件和系统睡眠接口，可作为后续配置实验的依据；并不证明这些选项能修复本机：

- [NVIDIA 595.84 电源管理说明](https://download.nvidia.com/XFree86/Linux-x86_64/595.84/README/powermanagement.html)
- [Linux 内核睡眠状态与 mem_sleep 接口](https://docs.kernel.org/admin-guide/pm/sleep-states.html)

这些结果证实自动采集在真实睡眠后能够运行，但不能用接口返回值证明用户已经看见登录画面。

用户贴出的错误对应固件方法 `\_SB.PC00.LPCB.EC.BRNS`、`_Q26`、`_Q27`。原始错误为索引 `0x11`（十进制 17）访问长度为 `0x0` 的 Package，触发 `AE_AML_PACKAGE_LIMIT`，随后当前方法和调用它的事件方法被中止。`_Qxx` 是 ACPI 嵌入式控制器的查询事件方法；具体事件含义需要本机固件表才能确认，不能单凭名称断定为合盖或亮度事件。

本次启动日志中这组错误有 168 条记录（三行一组），多个正常使用时段也出现，例如 11-12 14:43、15:31、18:11、22:38。因此它是需要跟踪的固件执行异常，不能仅凭“开盖时看到了它”认定它就是黑屏根因。

本机 `/usr/bin/nvidia-sleep.sh` 的 suspend 路径会先保存原控制台编号，再执行 `chvt 63`；resume 路径会尝试切回原编号。这个机制可能让开盖时暂时看到文字控制台上的旧 ACPI 报错。**这是与症状相符的解释，尚未在无法恢复的那一刻确认活动控制台，不能当成已证实的故障机制。**

取证工具现已补充独立 ACPI 日志、活动控制台 `/sys/class/tty/tty0/active`、当前 seat 与背光数值。后续用它们区分控制台切换、锁屏绘制和显示驱动问题；不通过屏蔽报错来宣称修复。

## 尚缺的关键证据

用户对现象的描述已足够。尚缺的是**一次无法返回桌面时，同一时刻的系统状态**，而不是更多 ACPI 报错照片。

| 需要自动记录什么 | 用于区分什么 |
| --- | --- |
| 实际显示的控制台编号与原图形会话编号 | 是否仍停留在 NVIDIA 使用的文字控制台、是否完成切回 |
| Xorg / GNOME 进程与线程状态、桌面和锁屏接口响应 | 图形会话是否存在、是否在等待或失去响应 |
| 显卡与 X11 查询响应、同一时段内核日志 | GPU/显示驱动卡住，还是桌面恢复过程卡住 |

这些状态需要结合判读，不能将某一个超时直接当成唯一根因。若整机在用户进程恢复之前卡死，用户级采集无法在那个阶段运行，届时需要进一步的系统级记录。

23:31 增强后的取证已部署，当前桌面/锁屏/显卡接口检查均成功。私有总线测试验证了在没有恢复完成信号时持续记录控制台/进程状态；整个验证没有触发真实睡眠。后续自然发生故障时，只需记录大概时间，以便对应日志；不要求为复现而反复合盖，也不把按键切换当成已验证修复。
